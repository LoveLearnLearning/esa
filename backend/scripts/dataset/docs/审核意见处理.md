## 训练集

### 1. 两条反向标签　✅ 完全成立，已修

核实：

```
record_learning_evidence_conf_001  用户「刚做完哈希表的练习，答错了」        → correct=True
record_learning_evidence_conf_002  用户「最小生成树那道选择题我选的 B，答案是 C」 → correct=True
```

**根因**：`generators/gen_new_tools.py` 的 `CONFUSION_ARGS` 把 `record_answer` 的
`correct` 写死成 `True`，完全不看话术说了什么。

**处理**：`correct` 改成在种子里**显式声明**，生成器不再猜。
凡是**语义标签**一律从种子读 —— 生成器能程序化决定的是参数怎么填，不是用户到底答对没答对。
顺带把回答也分了岔：答错时改成「记下了，这次没做对……要不要我帮你看看是卡在哪一步？」，
用同一句话打发对错两种情况，等于告诉模型对错无所谓。

**新增检查** `check_answer_polarity`：调用带 `correct` 布尔参数的工具时，
比对用户话术里的对错线索，只在线索**明确单向**时才报（同时出现或都没有就不报，避免变成假检查）。
配了 5 个用例，含「线索模糊时不乱报」。

## 评测集

### 1. 24 条多轮数据截断位置错误　✅ 完全成立，已修（本次最严重的一条）

这条抓得非常准。核实：24 条 `multi_turn_tool` 的 `n_turns_given` 全是 1，实际会话有 6 轮：

```
[0] user      我想复习计算机组成原理，期末考试还有 1 周。
[1] assistant 好的。需要我根据这个安排练习计划吗？      ← 错误地切在这里
[2] user      不好意思打错了，换成操作系统               ← 模型根本看不到
[3] function_call recommend_practice(course=操作系统)   ← 却要它预测这个
```

**这 24 条是无解题**，而且都算在 `CALL_TOOL` 桶里，会以假失败的形式拉低
工具选择准确率和参数完全匹配率。

**根因**：`evalset.py` 的 `cut_point` 写成了「第一条 `tool_call` **或** `assistant`」，
把中间那句应答当成了「模型该出手的地方」。中间应答属于**给定上下文**，不是被考察的输出。

**处理**：改成「有工具调用就切在**第一次 tool_call**；没有工具调用才切在第一条 assistant」。
修复后 21 条多轮题的切点全部为 3。

**新增断言** `assert_answerable`：判据不是「参数值没出现在前缀里」——
那会误伤一大批**本来就该推断**的参数（`activity_type='transfer'` 要从描述推、
英文检索词要从中文翻译、Skill 名要靠匹配）。真正的无解是
**「用户明明说了，却被截在给定范围之外」**，所以判据是「该取值出现在被截掉的某个用户轮里、
而前缀里没有」。命中就让评测集构建直接失败，不产出半成品。

（这个判据的第一版确实太严，一次报了 21 条误伤 —— 收窄之后归零。）

### 3. Skill 规则与 Gold 冲突　✅ 成立，**需要团队拍板**

核实：248 条 system 全都写着「先调用 load_skill 加载完整正文」，
而 gold 里首个调用是 `load_skill` 的只有 **1 条**，直接调学情工具的有 **72 条**。

你给的两个选项正是问题的核心，需要**知识图谱负责人 / 后端负责人拍板**：

- **Skill 是强制工作流** → gold 全部改成先 `load_skill`，数据要重造一批
- **Skill 只是可选路由建议** → 改后端 system prompt 的措辞，去掉「必须先」的语气

倾向后者：`load_skill` 每次多一轮往返，而 `loop_times = 3` 本来就紧张。
但这是后端的策略，不该由数据组单方面决定。

### 4. 工具结果统一为标准 JSON　❌ **不采纳，照做会造成分布偏移**

这条要明确反对，因为方向反了。

线上喂给模型的 observation 是这么来的：

```python
result_text = str(result)     # backend/agent/agent.py:252 和 :351，两处
```

对 dict 而言 `str()` 就是 **Python repr**：单引号、`True`/`None`。
也就是说 `{'allowed': True, 'result': None}` **正是线上真实形态**，
改成 `{"allowed": true, "result": null}` 才是偏离线上。

我们早就知道 Python repr 对 Qwen 不友好（它的工具调用能力是在 JSON 上训的），
所以 `esa/render.py:100` 留了 `OBSERVATION_FORMAT` 开关，当前值是 `"repr"`。
**正确的顺序是先让后端改成 `json.dumps(result, ensure_ascii=False)`，我们再切开关重跑** ——
这条已经写进 `后端问题反馈.md` 的 P0-3。数据侧单方面改，只会让训练和线上分家。

### 5. get_review_timing 属于未见工具　⚠️ 数字准确，诊断不对；建议采纳但改法不同

`evalset.py` 里写着：

```python
# L3 场景外推：这些 template 前缀整体留出，训练时完全不给。
L3_HOLDOUT_PREFIXES = ("get_review_timing__",)
```

**这是故意留出的**，专门测「模型有没有真正理解 `get_review_timing` 和 `get_mastery_level`
的区别」，而不是背下了见过的问法。所以「训练集里没有它的正例」不是切分事故。

但你的结论仍然成立，理由不同：**48 条占期望调用的 28.7%，确实重到会把总分拉成泛化分。**

**处理方式改成分层报，而不是拆两个文件** —— 拆文件会把 L1/L2/L3 三层压成两层，
「同分布」和「状态外推」的区别也一并丢了。

顺着这条还查出一个真问题：**`layer` 字段原先只是构建时的局部变量、用于打印统计，
从没写进每条记录的 gold**，所以按层判分根本做不到。已修：`layer` 进 gold，
`eval.py` 增加 `score_by_layer`，判分时自动多打一张分层表：


### 6. 与训练集仍有原句重合　✅ 成立，已修

核实：字面重合 13 条（后来数据变动后是 16 条）。但要区分两种：

- **真泄漏 4 条**：`修改参数` 的改口话术「等等，不是 8 周，是 3 周后就考」只带周数不带课程，
  不同课程渲染出同一句话，而**这句话本身携带答案**。
- **不算泄漏的 12 条**：`参数在历史轮` 的追问「那现在该练什么？」是**故意不带信息**的
  （这个状态的意义就是考「别重复追问、去上一轮取参数」），答案全在更早的轮次里，
  模型从这句话本身占不到任何便宜。

**处理**：改口话术一律补上课程和周数，让句子随事实组合唯一。
**新增断言** `assert_no_train_overlap`：评测题最后一句用户话若在训练集出现过
**且携带 gold 参数取值**，构建直接失败。修复后携带答案的重合为 **0 条**。

### 7. 部分参考答案本身有问题　✅ 两条都成立，已修

**（a）「帮我算 2 的 16 次方」→「这个用计算器算就行」**

这条抓得尤其好。它正是交接文档 5.6 记录的「把该调 B 的句子写成不该调 A 的负样本」，
那里写着「我在这上面栽了三次」—— **这是第四次**，而且当时加的检查（字面重复检测）根本抓不到它。

我顺着这条线索扫了全库，**同类还有 2 条**：

```
skill_neg_不该加载_01  「帮我算一下 15 的阶乘」   → 该调 calculator
rag_neg_04            「我数据结构掌握得怎么样」  → 该调 get_mastery_report
```

**处理**：这 4 条的教学意图是「工具边界」而不是「不调用」，所以改成
**真正调用正确工具**的混淆样本，诱饵工具仍然在场，回答里也仍然点明
「不用查知识库 / 不需要加载教学技能」—— 教学意图一点没丢，只是标签从「不调用」变成了「调对的那个」。

**新增检查** `check_negative_not_positive`：`hard_negative` 的回答里如果自己承认
「这个用计算器算就行」这类**另一个工具的职责**，就报错。自证的反面证据最好抓。
（第一版正则太宽，把寒暄样本的自我介绍「可以帮你规划练习、查学情、讲知识点」也报了，
已加指示代词锚定，并补了这条用例。）

**（b）快排 `T(n)=2T(n/2)+O(n)`**

也对。那是**恰好对半分**时的递推式，属于最好情况，不是平均情况的推导。已改写为：

$$T(n) = n - 1 + \frac{1}{n}\sum_{i=0}^{n-1}\left(T(i) + T(n-1-i)\right)$$

并说明解得 $T(n) \approx 1.39\, n \log_2 n$，比最好情况多约 39% 的比较次数 ——
结论同阶，但不能拿最好情况的式子当平均情况的证明。

## 我们顺带查出、审核里没提的一条

**`parse_output` 的 `_try_cast` 会丢类型**：它用 `json.loads` 还原参数值，
所以 `<parameter=lower>0</parameter>` 一律变成整数 `0`，即使 schema 把
`math_solver.lower` 声明成字符串（要能装下 `n`、`oo` 这类符号）。

后果是同一个模型，走 XML 解析器时参数匹配率和 schema 合法率会莫名掉几个点，
走 JSON 解析器时又是满分 —— 差的那几分测的是**解析器**不是模型。
判分侧已做归一（`args_equal` / `coerce_to_schema`），但线上的类型丢失还在，
已记进 `后端问题反馈.md` 的 P1-5。
