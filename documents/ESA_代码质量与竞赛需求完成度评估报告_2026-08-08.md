# ESA 代码质量与竞赛需求完成度评估报告

> 评估日期：2026-08-08  
> 评估对象：`main` 分支，HEAD `b01d18a`  
> 对标文件：XH-202620《面向一流学科建设的学科垂类大模型与创新应用开发比赛方案》  
> 评估性质：仓库证据审计。服务器 GPU、vLLM、Qdrant、正式知识库和公网部署未在本机复测；相关结论标记为“待服务器验证”，不因本机缺少环境直接扣分。

## 1. 结论摘要

ESA 已经不是简单聊天壳。仓库中存在一套较完整的计算机学科助学技术资产：多轮 Agent、SSE、工具调用、RAG/DocIR、结构化学习者画像、掌握度与前置知识图谱、教学策略路由、记忆隔离及 Flutter 多端界面。尤其是“诊断 - 教学干预 - 学习证据 - 掌握度更新 - 个性化推荐”的闭环，具备成为参赛核心差异点的基础。

但以 2026-08-08 当前仓库状态严格评审，作品尚未达到“可提交、可复现、可核验”的标准，主要原因是：

1. 主分支存在未清理的 Git 合并标记，Python 后端源码无法解析，属于阻断运行的 P0 缺陷。
2. RAG 路径接口发生重构漂移，测试和 CLI 仍导入已不存在的 `WORKSPACE_ROOT`。
3. 仓库没有版本化的正式 RAG collection/index/deployment 产物，也没有可直接复现的服务器配置、容器或 CI。
4. 赛题要求的 3 个典型问题准确性论证、至少 2 名真实目标用户反馈、3 分钟真实交互视频、伦理与安全声明均未形成交付证据。
5. 前端附件仍为模拟文件名；多模态、代码执行沙箱、教师端、前端分组等功能尚未闭环。

按赛题 100 分标准，仅根据当前仓库可核验证据估算为 **39/100**。这不是对产品潜力的评分，而是“今天把仓库交给评委能核验到什么”的保守评分。若先修复 P0、完成正式知识库部署和端到端验证，再补齐评测/用户/商业化证据，项目有机会进入 **72-82 分**区间。

## 5. 架构与模块评价

### 5.1 当前架构

```text
Flutter Web/iOS/macOS
        |
REST + SSE + Bearer Session
        |
FastAPI routers
        |
Agent orchestration
  | Prompt / Skills / Tools / Stream parser
  | Learner profile / memory / mastery / pedagogy router
  | RAG: DocIR -> chunk -> dense/BM25 -> RRF -> reranker -> evidence
        |
vLLM + Qdrant + SQLite + discipline resources
```

### 5.2 合理性与优势

1. **层次基本清晰。** Web 路由、服务、存储、Agent、RAG、DocIR 和 Flutter UI 有明确目录边界。
2. **RAG 管线设计优于普通 Demo。** 包含 DocIR、chunk、dense/BM25 多路召回、RRF、reranker、章节窗口、索引代次与指纹校验，并保留页码和来源标签。
3. **个性化不是纯提示词包装。** 画像、掌握度、学习证据、知识图谱、记忆模式和教学路由均有独立模型/存储/测试。
4. **安全基础有正向设计。** 密码使用 bcrypt；用户、会话、分组、画像查询普遍按 `user_id` 隔离；记忆存在 `isolated/no_write/normal` 模式；数学求值使用白名单 AST。
5. **前后端契约覆盖面较完整。** 31 个路由已覆盖基础账户与学习闭环，SSE 对反向代理缓冲也设置了响应头。

### 5.3 架构问题

1. `backend/core` 同时承载 Web、存储、模型、消息和服务，`backend/agent` 又直接依赖 `core`；边界更像技术分层而非稳定领域边界。
2. 存在未被 `webAPI.py` 使用的旧版 [`backend/core/web/chat.py`](../backend/core/web/chat.py) 和 [`backend/core/web/groups.py`](../backend/core/web/groups.py)，与 `routers/` 下同名实现并存，容易双轨漂移。
3. 单文件状态与 UI 过大：`app_state.dart`、`api_client.dart`、`profile_sheet.dart` 将多种业务职责集中在一起。
4. SQLite 每次操作新建同步连接，未统一设置 WAL、`busy_timeout` 或连接策略；同步画像构建也在异步消息路由进入模型前执行。低并发可用，但不适合作为“50+ 用户规模化”证据。
5. 模型、数据库、RAG 和 Web 配置没有形成统一 Settings/环境变量层，部署拓扑被硬编码进源码。

## 8. 具体问题清单

### P0 阻断问题

#### P0-01 主分支含未解决合并标记，后端无法解析

- 位置：[`backend/core/utils/models.py:98`](../backend/core/utils/models.py#L98)
- 现象：`<<<<<<< HEAD`、`=======`、`>>>>>>>` 被提交到主分支。
- 影响：任何导入 `backend.core.utils.models` 的后端启动、测试或工具脚本都会触发 `SyntaxError`；“核心功能闭环运行”无法成立。
- 建议：选择唯一字段定义并删除合并标记；增加 CI 中的 `python -m compileall -q backend` 和冲突标记扫描；合并保护要求 CI 通过。

#### P0-02 当前缺少可复现的服务器运行与部署交付

- 位置：[`backend/core/utils/config.py:18`](../backend/core/utils/config.py#L18)、[`backend/core/web/webAPI.py:32`](../backend/core/web/webAPI.py#L32)
- 现象：模型路径、显卡并行、RAG 模型路径、Qdrant、manifest、数据库路径均硬编码；`deploy/` 无跟踪文件，无 Docker/Compose、systemd、Nginx、环境变量样例或健康检查。
- 影响：评委无法按“作品代码确保可复现”要求部署；服务器差异会直接导致启动失败。
- 建议：提供 `.env.example`、强类型 Settings、依赖锁、模型/索引 manifest、启动脚本、Nginx SSE 配置、健康/就绪检查、备份恢复说明，并在全新服务器做一次按文档冷启动演练。

#### P0-03 官方要求的效果验证和提交材料未形成

- 证据：仓库未发现 `01-参赛信息` 至 `07-其他材料` 结构，也未发现伦理与安全声明、3 个准确性案例、2 名真实用户报告或 3 分钟真实交互视频。
- 影响：内容质量 20 分和用户认可 10 分几乎无法得分，也可能被判材料不完整。
- 建议：立即建立交付目录和材料负责人；不要等功能开发结束后再收集用户数据。

#### P1-04 生产安全与隐私配置不足

- 位置：[`backend/core/utils/config.py:14`](../backend/core/utils/config.py#L14)、[`backend/core/web/webAPI.py:81`](../backend/core/web/webAPI.py#L81)、[`backend/agent/agent.py:169`](../backend/agent/agent.py#L169)
- 现象：`DEBUG_MODE=True` 会打印模型思考与正文；CORS 允许所有来源；内部 metrics 端点无鉴权；会话令牌保存在 SharedPreferences；无统一内容安全/学术诚信策略。
- 影响：可能泄露学习内容或敏感推理；无法支撑伦理声明和真实用户试用。
- 建议：默认关闭 debug；日志脱敏；生产 CORS allowlist；保护内部指标；对敏感数据、学术诚信、提示注入和高风险内容给出可测试策略；前端优先使用安全存储或限制 Web token 暴露面。

#### P1-05 并发、超时和失败恢复不足

- 位置：[`backend/agent/agent.py:139`](../backend/agent/agent.py#L139)、[`backend/core/web/routers/chat.py:297`](../backend/core/web/routers/chat.py#L297)、[`backend/core/stores/base_sqlite_store.py:20`](../backend/core/stores/base_sqlite_store.py#L20)
- 现象：模型工具通过 `asyncio.to_thread` 执行但无统一超时/取消/熔断；消息生成接口无用户级并发和速率限制；SQLite 无 WAL/忙等待策略；Agent 达到循环上限后没有明确的终止说明。
- 影响：慢工具或并发请求可占满线程/模型槽位；50+ 用户验证风险高；工具循环耗尽时可能没有可见最终答复。
- 建议：给模型与工具增加 deadline；按用户/全局限制并发；统一错误事件；SQLite 开启 WAL 和 `busy_timeout` 或迁移 PostgreSQL；增加超限 fallback 回复。

#### P1-06 测试与实现已经漂移，缺少 CI 门禁

- 结果：本机后端 `pytest` 在收集阶段被 RAG 导入错误阻断；源文件还存在 SyntaxError。Flutter `analyze` 通过，但 8 个 widget 测试中 6 个通过、2 个选择性测试失败。由于本机 Flutter SDK 解析了不同的传递依赖，该结果需要在锁定 SDK 的服务器/CI 复核。
- 覆盖率：**无法计算**，不是 0%；后端目前无法完整收集且仓库没有覆盖率门禁。测试行比例不能替代覆盖率。
- 建议：固定 Python/Flutter 版本；建立 CI 矩阵；最少门禁为冲突标记、compileall、pytest、coverage、flutter analyze、flutter test、Tool Schema 快照一致性和构建 smoke test。

#### P1-07 文档与实现状态漂移

- 证据：`TODO.md` 仍称正式 Tool Schema 导出脚本未完成，但仓库实际存在两个导出器；注册点静态计数为 23，而版本化 `tool_schemas.json` 只有 22 项；README/TODO 状态日期早于最新提交。
- 影响：团队无法可靠判断“已完成”和“待完成”，评委也会质疑材料可信度。
- 建议：只保留一个导出入口；CI 导出后 `git diff --exit-code`；以可执行验收项管理 TODO，开发日志不作为当前事实来源。

#### P1-08 内容质量、商业化和用户认可没有量化数据

- 影响：直接损失官方评分中的 40 分（内容质量 20、商业化 10、用户认可 10）。
- 建议：见第 11、12 节，先建立评测协议和真实试用，再扩充低价值功能。

#### P1-09 知识产权与数据合规证据不足

- 现状：仓库跟踪多篇 PDF，但未提供逐项许可、来源清单或可再分发依据；无模型许可证、数据卡、第三方组件清单和生成数据标识规范。
- 影响：赛题要求作品拥有完整知识产权且无权利瑕疵，材料不完整会形成提交风险。
- 建议：建立 `THIRD_PARTY_NOTICES`、语料许可表、模型/embedding/reranker license 表、数据处理说明；无法再分发的 PDF 只提交下载脚本与 hash，不直接打包。

### P2 中优先级问题

#### P2-01 大文件和长函数增加变更风险

- 典型：`mastery_store.py` 966 行、`profile_sheet.dart` 752 行、`app_state.dart` 621 行、`api_client.dart` 520 行。
- 建议：按“证据写入/掌握度推断/复习调度/报告”拆分 mastery；按功能拆分 profile sheet；将 API client 分为 auth/chat/profile/learning；状态按领域 Store/Controller 拆分。

#### P2-02 重复和遗留模块未清理

- `backend/core/web/chat.py` 与 `routers/chat.py`、`backend/core/web/groups.py` 与 `routers/groups.py` 并存，当前 `webAPI.py` 只挂载 `routers/` 版本。
- 建议：确认无外部引用后删除或标记 deprecated，并用 import graph/测试保护唯一入口。

#### P2-03 依赖与开发规范不完整

- Python 依赖大多无精确版本，无 `pyproject.toml`、lint/type-check 配置、开发依赖和 lock；README 未声明 Python 版本、CUDA/驱动矩阵。
- 建议：采用 `pyproject.toml` + lock；固定 Python、CUDA、torch、vLLM、transformers 兼容矩阵；启用 Ruff、Pyright/Mypy、pre-commit。

#### P2-04 前端测试覆盖薄弱

- 4 个文件、208 行测试覆盖登录、输入法、Markdown 和选择性，但未覆盖 API 错误、SSE 断线重连、会话持久化、画像/记忆、响应式、附件、分组和无障碍。
- 建议：优先补关键用户旅程集成测试，而不是追求纯组件数量。

## 9. 潜在 Bug 风险补充

1. **Agent 循环耗尽：** `run`/`run_stream` 在模型持续发起工具调用时退出循环，但没有生成“达到上限”的用户可见结论。
2. **工具异常范围不完整：** ToolRegistry 只统一处理 `ValueError/TypeError/RuntimeError`；其他网络、解析或文件异常可能穿透并终止一轮 Agent。
3. **SSE 中断一致性：** 用户消息在推理前落库，助手消息只在 `complete` 后落库；断线时客户端看到的部分回复可能无法在刷新后恢复。
4. **数据库竞争：** 多个同步 SQLite 连接缺少统一 pragma 和重试，在并发写入对话、画像、学习证据时可能出现 `database is locked`。
5. **公开可观测性端点：** `/internal/metrics*` 无鉴权或网络隔离代码，可能暴露内部运行信息。
6. **离线模式误用：** `kOfflineMode` 当前为 false，但代码内置模拟登录、模拟 RAG 和固定答案。发布流程应强制生产构建禁止开启，并在离线 Demo 显著标识，避免验证材料失真。

## 11. 最应强调的竞争力

### 11.1 把产品定义从“AI 学习助手”收窄为“证据驱动的计算机学科自适应学习系统”

通用聊天、Markdown 和搜索很容易同质化。演示与 PPT 应围绕以下闭环展开：

1. 学生提交真实作答或代码。
2. 系统识别知识点并按可靠性记录学习证据。
3. 掌握度模型更新，不把一次偶然答对等同于真正掌握。
4. 前置知识图谱定位根因，而不是只解释当前错题。
5. Pedagogy Router 选择主动回忆、渐进提示、Teach-back 等策略。
6. 下一次推荐与讲解深度随学习历史自适应。
7. RAG 为关键知识提供可回查教材/课程来源。

这是项目最有辨识度的叙事，也是对赛题“个性化与自适应”“复杂问题求解”“深度贴合场景”的直接响应。

### 11.2 用现有结构化资产形成可视化证据

- 展示 47 门课程、473 个知识点、439 条前置依赖，而不是只展示聊天界面。
- 增加“为什么推荐这道题/为什么降低讲解难度”的可解释面板。
- 展示一名学生跨 3 次练习的掌握度变化、错因和推荐变化。
- 教师端只做一个高价值页面：班级知识薄弱热力图 + 前置根因 Top 5 + 可下钻学生证据。它能同时提升助教场景、实用度和商业化叙事。

### 11.3 以可靠性而非模型大小取胜

模型微调是建议项，不是硬性门槛。在截止期内，优先级应为：

1. 真实权威语料与页码引用；
2. 典型问题准确性和拒答/降级评测；
3. 学习效果或教师效率数据；
4. 稳定 Demo；
5. 最后才是只有在基准上明显增益的 LoRA。

不要只宣传“Qwen3.5-122B-A10B”。应报告相同测试集上：无 RAG、仅 RAG、RAG + 教学策略、如有 LoRA 的准确率/引用正确率/教学质量对比。

### 11.4 建立可信内容与合规护城河

- 每个引用都能点击回到原文页码。
- 区分“模型生成”“知识库证据”“系统推断的画像”“用户显式设置”。
- 对低置信度掌握度、未知知识点和检索失败明确降级，不伪造来源。
- 提供学生数据脱敏、导出、删除和保留周期说明。
- 对作业场景加入学术诚信模式：默认提示与诊断优先，完整答案由课程策略控制并留痕。

## 12. 必做评测与用户证据

### 12.1 三个官方典型问题案例

建议固定为可重复、可评分的三类：

1. **知识可信度：** 数据结构/算法概念题，标准答案 + 指定教材页码，测事实准确率、引用正确率和引用可达率。
2. **复杂问题求解：** 一段有边界 Bug 的代码，测定位正确率、分步提示质量、最终代码通过率和工具调用正确率。
3. **个性化自适应：** 同一问题给低/中/高掌握度画像，测讲解深度、提示级别、推荐内容是否按预期变化。

每个案例至少保存输入、固定模型/索引版本、完整输出、标准答案、评分 rubric、人工评审人、机器可执行结果和截图/视频。

### 12.2 最低指标集

| 类别 | 建议指标 |
|---|---|
| 内容 | 答案准确率、关键点覆盖率、幻觉率 |
| 引用 | 引用正确率、引用可达率、原文支持率 |
| Agent | 工具选择正确率、参数正确率、循环完成率、失败恢复率 |
| 教学 | 错因定位一致率、提示级别适配率、前后测提升 |
| 性能 | 首 token 延迟、总响应时间、P95、并发 1/10/50、错误率 |
| 安全 | 越权隔离、提示注入、敏感信息日志、伪造引用、数据删除 |

### 12.3 用户验证设计

- 最低：1 名计算机专业教师 + 1 名目标年级学生，各完成至少 5 个真实任务。
- 更有竞争力：30-50 名学生、1-2 周，记录任务数、留存、完成时间、前后测和满意度；争取 50+ 规模加分。
- 反馈不能只有“好用”。必须记录身份、时间、频次、场景、基线、结果、问题和改进。
- 教师指标建议用“批改/诊断耗时下降”；学生指标建议用“前后测提升、独立完成率、提示次数下降”。
