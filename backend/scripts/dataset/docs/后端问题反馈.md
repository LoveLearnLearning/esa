## ~~P0-3　`observation` 用 `str(result)` 而不是 `json.dumps`~~　✅ 已于 2026-08-11 修复

result_text = json.dumps(result, ensure_ascii=False)

## P1-1　`get_time` 有两个 bug

```python
return datetime.now(timezone.utc).strftime("%D-%H:%M:%S")   # agent/tools/tools.py:46-49
```

1. **返回 UTC，而学生在东八区**。学生问「今天几号」「还有几天考试」，在每天 08:00 之前会**差一天**。
2. **`%D` 展开成 `%m/%d/%y`** ——「08/10/26」这种美式两位年份有歧义（是 2026 年 8 月 10 日还是 2010 年？），
   而且 `%D` 是 glibc 扩展，不保证可移植。

**建议**：`datetime.now(ZoneInfo("Asia/Shanghai")).strftime("%Y-%m-%d %H:%M:%S")`。

数据里我们已如实复刻现状（`dataset/esa/fixtures.py:531-540`）。你们改了我们重生成那 5 条即可。

## P1-3　并行工具调用的消息结构，训练侧对不上

## ~~P1-5　`parse_output` 的 `_try_cast` 丢类型：字符串 `"0"` 会变成整数 `0`~~　✅ 已于 2026-08-11 修复

`_try_cast` 用 `json.loads` 还原参数值（`backend/core/utils/parser.py`），
所以 XML 里的 `<parameter=lower>0</parameter>` 一律得到整数 `0` ——

具体踩到的一处：`math_solver` 的 `lower` / `upper` / `point` 在 schema 里是 `"type": "string"`
（`math_tools/math_solver.py` 的注册块），因为它们要能装下 `n`、`oo` 这类符号表达式。
模型正确地写出 `lower="0"`，经 `_try_cast` 之后工具收到的是 `0`。

**影响**：

- 对 `math_solver` 本身是良性的 —— `sympify(0)` 和 `sympify("0")` 结果一样。
- 但它**破坏了工具自己的 schema 契约**，任何依赖参数类型的工具都会中招。
- 对我们的评测更直接：同一个模型，走 XML 解析器时参数匹配率和 schema 合法率会莫名掉几个点，
  走 JSON 解析器时又是满分 —— 差的那几分测的是解析器，不是模型。
  我们已在 `dataset/esa/eval.py` 的 `args_equal` / `coerce_to_schema` 里做了归一，
  **但那是判分侧的补偿，线上的类型丢失还在。**

~~**建议**：`_try_cast` 参照 schema 里声明的类型来转，而不是无条件 `json.loads`。~~

**✅ 你们已经改了，而且比我们建议的更彻底**：新增 `backend/core/utils/tool_arguments.py`

## P1-4　`DATASET_GENERATION.md` 里有三处会直接踩坑

这份文档写得很好，方案本身我们基本照做了（程序化生成场景、真实执行工具、
自动校验清单、按模板整组切分防泄漏）。但有三处和实际情况对不上，都会造成实打实的损失：

**① `template: qwen3_5` 这个模板不存在，训练会直接报错**

文档第一节写「LLaMA-Factory 会根据 `template: qwen3_5` 把结构化数据转换成 Qwen3.5
原生工具调用文本」。我们在 LLaMA-Factory 0.9.4 源码里 grep 过，**`qwen3_5` 零处命中**，
实际有的是：

```
qwen / qwen2_audio / qwen2_omni / qwen2_vl / qwen3 / qwen3_nothink
qwen3_omni / qwen3_omni_nothink / qwen3_vl / qwen3_vl_nothink
```

应当用 **`qwen3`**，而且不能用 `qwen3_nothink` —— 后者不产出 `<think>`，
你们的 `StreamOutputParser` 会把整个回答当 reasoning 吐出、正文为空。

**② 示例里的 observation 结构是错的，我们照抄踩了坑**

文档第四节的工具调用样本写着：

```json
{ "from": "observation", "value": "{\"value\":5.0}" }
```

而 `calculator` 真实返回的是 `{"expression": "...", "result": 5}`
（`math_tools/calculator.py:167-170`）—— 没有 `value` 这个字段。

我们照着这个示例造了 63 条样本（calculator 21 / bitwise 20 / math_solver 22），
全部在教模型消费一个线上不存在的结构，而所有校验都是绿的。已经改成
`import` 你们的真实函数执行取值了，但**建议把文档里的示例也更正**，
不然下一个照做的人会再踩一遍。

同一节 `save_core_memory` 的 `{"success":true}` 也是错的，真实是
`{"saved": ..., "memory_key": ..., "content": ..., "category": ..., "profile_projection": ...}`。

**③ 顺带确认一件好事：基座型号写着 `Qwen/Qwen3.5-122B-A10B`**

按 Qwen 的命名惯例，`A10B` 是「激活 10B 参数」，也就是 **MoE 而非 dense**。
我们此前一直标记为「未知」，显存和吞吐规划卡在这。如果确实是 MoE，
8×A800 的部署方案要按 MoE 来配。开训前建议还是 `cat <模型路径>/config.json` 确认一次
（看 `architectures` 里有没有 `Moe`、有没有 `num_experts`）。
