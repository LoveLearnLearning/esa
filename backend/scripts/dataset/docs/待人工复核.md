### [ ] `hardneg_000`

- 类别：`hard_negative`　知识点：`quicksort_analysis`　模板：`hardneg__000`

**用户**：快速排序的平均时间复杂度是多少，为什么是这个结果？

**回答**：

```markdown
先不往下看，花十秒想一个问题：「平均情况」和「最好情况」用的是同一个递推式吗？想好了再对答案——这一问正是下面要澄清的地方。

快速排序平均时间复杂度是 $O(n \log n)$。

先说直觉：每次 partition 要扫一遍，$O(n)$ 次比较；如果每次都大致对半分，递归深度是 $O(\log n)$ 层，每层合计 $O(n)$，所以总量 $O(n \log n)$。

不过要说清楚一点：$T(n) = 2T(n/2) + O(n)$ 是**恰好对半分**时的递推式，那是最好情况，不是平均情况的推导。平均情况要对基准的所有可能位置取期望：

$$T(n) = n - 1 + \frac{1}{n}\sum_{i=0}^{n-1}\left(T(i) + T(n-1-i)\right)$$

解这个递推得到 $T(n) \approx 2n\ln n \approx 1.39 n \log_2 n$，仍是 $O(n \log n)$——比最好情况多了约 39% 的比较次数。所以「平均和最好同阶」这个结论是对的，但**不能拿最好情况的式子当平均情况的证明**。

最坏情况是 $O(n^2)$：每次选的基准都是最大或最小元素时，划分极度不平衡，递归深度退化成 $n$ 层。这也是实际实现要随机化选基准的原因。
```

### [ ] `hardneg_001`

- 类别：`hard_negative`　知识点：`process_scheduling`　模板：`hardneg__001`

**用户**：进程调度里的优先级是怎么确定的？

**回答**：

```markdown
进程优先级的确定方式取决于调度算法，主要分两类：

**静态优先级**——进程创建时确定，运行期间不变。依据通常是进程类型（系统进程高于用户进程）、资源需求、用户设定的 nice 值。实现简单，但容易造成低优先级进程饥饿。

**动态优先级**——运行期间根据行为调整。常见规则有两条：
- 等待时间越长，优先级越高（老化 aging，用来防饥饿）
- 占用 CPU 时间越长，优先级越低（倾向于 I/O 密集型进程，提高整体响应性）

Linux 的 CFS 严格说不用优先级队列，而是用虚拟运行时间 vruntime，每次挑 vruntime 最小的进程运行，nice 值影响 vruntime 的增长速率——本质上是同一个思路的连续化版本。
```

### [ ] `hardneg_002`

- 类别：`hard_negative`　知识点：`cache_mapping`　模板：`hardneg__002`

**用户**：Cache 的命中率怎么提高？

**回答**：

```markdown
提高 Cache 命中率主要从三个方向入手，对应三类缺失：

**强制缺失（compulsory）**——首次访问必然缺失。用预取（prefetch）和增大块大小来缓解，利用空间局部性。

**容量缺失（capacity）**——工作集超过 Cache 容量。增大容量，或者改造程序减小工作集，典型手段是循环分块（loop tiling），把大矩阵拆成能装进 Cache 的小块。

**冲突缺失（conflict）**——多个地址映射到同一组。提高相联度（组相联替代直接映射），或者调整数据布局避免跨步访问恰好撞上同一组。

程序层面最有效的其实是改善局部性：按行遍历行主序存储的二维数组、把结构体数组（AoS）改成数组结构体（SoA）、避免大跨步访问。
```

### [ ] `hardneg_003`

- 类别：`hard_negative`　知识点：`memory_hierarchy`　模板：`hardneg__003`

**用户**：什么是存储器层次结构？为什么要分这么多层？

**回答**：

```markdown
先不往下看，试着自己答一句：分层能成立，靠的是程序的什么性质？想好了再对答案。

存储器层次结构是把不同速度、容量、成本的存储器按层组织：寄存器 → L1/L2/L3 Cache → 主存 → SSD/磁盘。越靠上越快、越小、越贵。

**为什么要分层**——因为速度和容量在物理上无法兼得。SRAM 快但每比特成本高、集成度低；DRAM 便宜容量大，但访问延迟比 SRAM 慢一到两个数量级；SSD 和磁盘更便宜，又比 DRAM 慢三到五个数量级。单独用任何一种都不划算。

**为什么分层有效**——依赖程序的局部性原理：
- 时间局部性：刚访问过的数据很可能马上再访问（循环变量）
- 空间局部性：访问了某地址，附近地址很可能也要访问（数组遍历）

有了局部性，绝大多数访问都能在靠上的层命中，于是整体表现接近上层的速度、接近下层的容量。这是整个层次结构成立的前提——如果程序访问完全随机，分层就没有意义了。
```

### [ ] `hardneg_004`

- 类别：`hard_negative`　知识点：`tcp_handshake`　模板：`hardneg__004`

**用户**：帮我回忆一下 TCP 三次握手的过程。

**回答**：

```markdown
TCP 三次握手的过程：

1. **SYN**：客户端发送 `SYN=1, seq=x`，进入 SYN_SENT 状态。
2. **SYN-ACK**：服务端回 `SYN=1, ACK=1, seq=y, ack=x+1`，进入 SYN_RCVD 状态。
3. **ACK**：客户端回 `ACK=1, seq=x+1, ack=y+1`，双方进入 ESTABLISHED。

**为什么是三次而不是两次**——核心是要让双方都确认「自己的发送能力」和「对方的接收能力」都正常。注意缺口在服务端那一侧，不在客户端：两次握手之后客户端其实已经全部确认完了（服务端 ack 了 $x+1$，说明它收到了；自己也收到了 SYN-ACK，说明它能发）。缺的是服务端不知道自己的 SYN-ACK 有没有送达，因而确认不了客户端的接收能力。第三次 ACK 补的正是这个缺口。

更实际的理由是防止历史连接：如果客户端一个早已超时的 SYN 在网络里滞留后才到达服务端，两次握手下服务端会直接建立连接并一直等待，浪费资源。三次握手时客户端发现这不是当前连接，会回 RST 中止。
```

### [ ] `hardneg_005`

- 类别：`hard_negative`　知识点：`binary_tree_traversal`　模板：`hardneg__005`

**用户**：二叉树的中序遍历我总是写错，能讲讲吗？

**回答**：

````markdown
中序遍历的顺序是**左 → 根 → 右**。写错通常错在递归的位置，记住这个口诀就行：中序的「中」指的是根在中间。

```python
def inorder(node):
    if not node:
        return
    inorder(node.left)   # 左
    visit(node)          # 根 ← 根在中间，这就是"中序"
    inorder(node.right)  # 右
```

对比一下就很清楚：前序是 `visit` 放最前（根左右），后序是 `visit` 放最后（左右根），中序是放中间。三种遍历的代码结构完全一样，只有 `visit` 的位置不同。

一个很有用的性质：**二叉搜索树的中序遍历结果是有序的**。这也是检验 BST 是否合法的常用方法。

你要是想练一下，可以给我一棵具体的树，我们一起走一遍——或者你先写出答案，我帮你看哪一步偏了。
````
